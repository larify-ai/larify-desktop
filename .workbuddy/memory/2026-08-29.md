## 本机硬件（2026-08-29 现场读取，重要）

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen AI 9 H 365，10 核 20 线程（Zen 5） |
| iGPU | AMD Radeon 880M，12 CU（RDNA 3.5），驱动 32.0.13070.1002 |
| NPU | XDNA 2，50 TOPS |
| 内存 | 31.1 GB |
| 系统 | Windows 11 25H2（build 26200）→ 满足 NPU 加速硬性要求 |

**结论：本机可做本地部署，无需独显。**

- 取硬件信息的方法：`wmic` 和安全策略被禁、PowerShell 工具 stdout 抓不到，
  **可用 node 的 `os.cpus()` / `os.totalmem()` 取 CPU 与内存**；显卡要用 PowerShell 的
  `Get-CimInstance Win32_VideoController` 写文件再 Read 才能拿到。
- WMI 报的 `AdapterRAM = 0.5GB` 只是 UMA 预分配值，**不代表核显可用显存**，别被误导。
- 核显是带宽受限：decode 速度 ≈ 内存带宽 ÷ 模型体积 → **MoE 模型远优于同等体积 dense**。
- 实测参考：同款 880M 用 llama.cpp+Vulkan 跑 Gemma-4 E4B ≈ 16 tok/s；
  同款 CPU 跑 granite-3.0-3b Q8 ≈ 57 tok/s（MoE，激活 800M）。
- **主推 AMD Lemonade**（官方，专给 Ryzen AI 300/400）：一键装完即 OpenAI 兼容服务
  `http://localhost:13305/v1`；三种 NPU 模式，其中 **Hybrid = NPU 做 prefill + iGPU 做 decode**
  是最关键的（prefill 算力密集、decode 带宽密集，各取所长）。Ollama 不支持 AMD NPU，浪费一半硬件。
- 本机甜点模型：**Qwen3-30B-A3B（MoE，Q4 ~17GB，15-25 tok/s）**；最快是 Qwen3-4B / Gemma-4-E4B。
- larify 接入：用 `@ai-sdk/openai-compatible` 指向 `http://localhost:13305/v1` 即可，
  **不必打包 node-llama-cpp**。
- 注意：NPU 需 Windows 11；进 BIOS 调大 UMA Frame Buffer Size；31GB 内存实际能给模型约 20-24GB。

## 调研：近眼显示 / 远像光学（"眼前小屏看成远处大屏"的技术）

用户提问：眼前的显示屏能看出很远的距离，这是什么技术。

### 结论要点（已核实）
- 本质不是"投远"，而是**改变入眼光线的发散度**；技术名：虚像显示 / 准直光学 collimation。
- 核心公式：`D = 1/距离(m)`。屏幕 4cm = 25 D（人眼极限仅 10~14 D，故裸看必糊）。
  薄透镜：`1/f = 1/u + 1/v`，u=0.05m、v=−2m → f≈5.1cm、**光焦度 ≈ +19.5 D**，
  把调节需求降到 0.5 D → 感觉在 2 m。≥6 m 称"光学无穷远"（<0.17 D）。
- 三类形态：VR/AR 头显（NED，3~5cm → 1.3~2m / ∞）、桌面远像屏（20~33cm → 3~8m）、
  车载 HUD（→ 7~10m 以上）。
- 六种光学方案：非球面镜 / 菲涅尔 / **Pancake（光效损失 65~75%）** / Birdbath /
  波导（几何·衍射，衍射 FOV 对角约 70°）/ Maxwellian 视网膜投影（eyebox 极小，绕开对焦）。
- 自由曲面镜是远像屏与 HUD 的共同核心；**直径 400mm 约 1000 元、500mm 约 2000 元**（动脉网）
  ——这是远像屏卖大几千的主因。
- 两大坑：**VAC 会聚-调节冲突**（解法：varifocal/light field/holographic/Maxwellian，均未大规模商用）+ 光效。
- 国内标准：2026-05-29 发布《远像技术在近视防控中的应用专家共识（2026）》，
  《中华眼视光学与视觉科学杂志》2026;28(6):401-409，DOI 10.3760/cma.j.cn115909-20260214-00064。
  指标：PPD>60、畸变<1%、虚像平整度<0.05D。

## 调研：智能眼镜上的显示光学货架件（追问"现在有这样的组件么"）

### 关键认知（纠正一个易错点）
智能眼镜显示分三层，**"看远"在第 2 层（光机）就已完成**——光机输出的本来就是准直光，
虚像天然在无穷远。第 3 层波导/Birdbath 只负责把光搬到眼前 + 让现实光透过，**不改变虚像距离**。
所以 AR 眼镜虚像距离固定为无穷远，是光学结构的必然，不是可调参数。

### 可采购货架件（2026-08 在售，重要参数已核实）

  光通量 6 lm、配 30° 衍射波导入眼 6000 nits、典型功耗 98 mW、体积 0.18cc、480Hz、PPD 33.3。
  有单目全彩 AR 开发套件。JBD 全球 MicroLED 微显示市占率 >70%，已用于全球近 50 款智能眼镜。
- **浩宇微显 LE-JAR13E03 开发套件**（最适合个人开发者）：单绿 640×480、FOV 30°、出瞳 3.3mm、
  畸变≤1%、0.15cc / 0.04g / 0.2W、**MIPI+SPI**、配驱动板双 Type-C 供电上电即亮、预留 BOOT 与调试焊盘。
  同厂波导模组：单目 FOV30°（透过率85%/入眼1600nits）、双目 FOV25°（94%/2000nits），
  出瞳距 20mm、eyebox 12×10mm、**虚像距离无穷远**、侧投。
- **视涯/TDO GEJ-35（SY049WDG09）Birdbath 双目模组**：0.49" Si-OLED×2、1920×1080、1800nits、
  MIPI、FOV 41~43°、屈光度 0~−5D、IPD 63.5mm、**$250~370/片且 1 片起订**。
  视涯 Si-OLED 全系 MIPI，0.32"~1.03"（1.03" 2560×2560 配 Pancake VR 模组）。

### 工程坑（已核实）
- **衍射波导光效 < 1%**（行业公开痛点）→ 必须配几千 nits 的 MicroLED，Si-OLED 配波导入眼亮度会很惨。

- eyebox 小（12×10mm）、出瞳距 20mm，光机-波导-眼睛三者结构必须锁死。
- 光机与波导的**光学耦合标定需要六维调整架 + 积分球**，别手工对准。
- 主动调光（电致变色）已成透视式 AR 标配（Snap Spectacles、Xreal Air 2 Pro），BOM 别漏。
- AR 眼镜光学件占 BOM 约 43%，是价值与壁垒最高的环节。

## 调研：Anthropic MHS（Model Hardware Standard，模型硬件标准）

用户提问："claude 的 mhs 莫得了 hardward standard"（= Claude 的 MHS 模型硬件标准）。

### 结论要点（已核实，官方 2026-08-27 发布）
- **MHS = 物理世界的 MCP**。Anthropic 不造机器人身体，先造"AI 连身体的接口"。
  官网 https://www.modelhardwarestandard.com/ ；当前 **research preview 需申请**，
  **规范本身尚未公开**，计划开源但**无日期**。Model-agnostic（任何 MCP 客户端可用）。
- 起源：Anthropic 的 Alek Kemeny × HHMI Janelia 博士后 Arco Bast。
  原型是"把整个 rig 状态塞进共享内存字典"，让多厂商仪器以内存速度互相对话。
- 机制三层：① 标准化 driver（设备跨网络可被发现）② **自然语言 tags → 自动生成参考文件**
  （能测什么 / 能调什么 / 强制哪些安全限）③ 运行时统一表示（states + procedures manifest，
  或共享内存字典）。原语只有 `read` / `write`。
- 接入三条路：MCP / CLI / 代码文件。长任务时 Agent 把驱动命令**链成确定性脚本**，
  脱离模型在线推理跑——这是关键设计。
- 硬数据：QuEra 激光锁定 150s→6s、58%→99.3%（700 次盲测），PID 残余误差 15.7mV→1.55mV；
  CMU 三台不兼容仪器 8 小时集成（供应商要数周）、实验快 3 倍、**6 种人为故障在设备动之前全拦**、
  自主发现 R²<0.9 后降浓度重跑到 R²>0.98；Genentech 自主优化出水流速 ~140µL/s vs BSA 10µL/s；
  Janelia 7 个厂商程序归一、新硬件接入 数天→几分钟；UW 6 台仪器不到一周。
- 生态：AWS(Strands Robots)、Universal Robots、Doosan、Tecan、QIAGEN、Danaher、
  MBF Bioscience(ScanImage)、Automata；下一波 **Hugging Face LeRobot + Raspberry Pi**。
- 局限：模型缺物理直觉（Genentech 气泡案例——它只会重试而不会换孔）、不支持无编程接口硬件、
  Agent 过于谨慎会夜里等人确认、需喂大量上下文、GUI-only 设备无从校验。
- 争议：**规范不公开却叫"标准"**（HN 尖锐批评）；**绕开 ROS 2**（目标高度重合）；
  **EU Machinery Regulation 2023/1230 于 2027-01-20 生效**——约束机械臂速度/角度的规范
  在欧盟可能被认定为"受监管的安全部件"；安全边界放在 driver（软件路径）内存疑，
  BaristaLabs 主张硬急停/物理限位必须留在 Agent 路径之外。

### 追问：read/write 的参数是什么、为什么两个就够（已补进报告 §2.2）

用搜索引擎确认过：**MHS 的 schema 全网无公开信息**（搜 MHS 全是撞名的 Message Handling
System / Managed Health Services），所以只能讲官方博客可确认部分 + 体系结构原理，推断处需标注。

核心澄清：
- **不是裸 `read(address)`，是读写「具名变量」**。参数是语义化资源标识符
  （`read("incubator.temperature")`），语义由参考文件定义（变量名/类型/单位/读写性/
  取值范围与安全边界/副作用/自然语言描述——**字段清单属推断，非公开 schema**）。
- 为什么两个够，三层论证：① 物理上数字可控设备剥到底就是传感器(读)+执行器(写)，
  证据是 **Modbus**（0x03/0x06/0x10 几个功能码统治工业界 40 年）；
  ② 真正干活的是命名空间与元数据而非原语（类比 HTTP GET/POST——动词只是意图，语义在参数里），
  复杂度被转移到数据模型层；专用 API 是 N×M 集成成本，统一 read/write 是 N+M，
  这是 CMU「8 小时 vs 数周」的由来；③ 复杂动作下沉成 **procedure**，
  = 一次 write 触发 + 多次 read 轮询状态机 + 一次 read 校验。
- 不够的四处：流式数据（需 subscribe/stream）、原子性与事务、硬实时（故需确定性脚本）、
  语义鸿沟（Genentech 气泡案例——read/write 搬得了数据搬不了物理直觉）。

## 调研：开发板级 MHS（树莓派 / 嵌入式落地视角）

### 信息边界（重要，已多方验证）
Raspberry Pi 的 MHS 集成**公开信息只有官方那一句**（"following successful tests using their
Camera MHS Driver"），所有二手报道都在复述。**无 schema / 代码 / SDK**。

### 树莓派产品与技术栈（2026-08 已核实）
- 计算：Pi 5（BCM2712 + **RP1 南桥**，PCIe 2.0 x4；有 16GB/$120 版）、CM5（工业 SoM，
  pin 兼容 CM4）、Pi 500+、Zero 2 W、**Pico 2（RP2350：双核 M33 + RISC-V 可切换，
  520KB SRAM / 16MB Flash / PIO）**。
- AI：**AI Camera（Sony IMX500，神经网络跑在传感器内，输出检测结果而非图像；
  CSI-2，RGB+红外，走 libcamera）**、AI HAT+（Hailo-8 13/26 TOPS）、
  **AI HAT+ 2（2026 新品，Hailo-10H，40 TOPS，8GB RAM，支持 LLM/VLM）**。
- 相机栈：libcamera → rpicam-apps（rpicam-hello/jpeg/still/vid/raw/detect）/ Picamera2。
  **旧栈 raspivid/raspistill/初代 Picamera 已废弃，老教程代码基本跑不了。**

### Pi 5 GPIO 的三个坑（已核实，会踩）
1. **RPi.GPIO 在 Pi 5 彻底失效**——GPIO 寄存器在 RP1 不在主 SoC，而 RPi.GPIO 用 /dev/mem
   直访问主处理器寄存器，报 "This module can only be run on a Raspberry Pi!"。**架构决策不是 bug**。
   新方案走 Linux 内核 `/dev/gpiochip`。
2. 选型：新项目 **gpiozero**（官方推荐）/ 底层 **lgpio** / 救老代码 **rpi-lgpio**（drop-in）。
3. ⚠️ **gpiochip 编号官方文档互相矛盾**——一处说 Pi 5 用 chip=4，另一处说排针用 gpiochip0。
   **必须 `gpiodetect` / `gpioinfo` 实测**；最省事是 `GPIOZERO_PIN_FACTORY=lgpio` 让它自己选。
   另：gpiozero **2.0.1.post1（2026-07）** 修复了 pip 安装时 lgpio pin factory 的 bug。
4. PEP 668：Pi OS 上 pip 需 venv，GPIO 项目用 `--system-site-packages`。

### 关键架构判断
**MHS driver 跑在有 OS 的主机（Pi 5 / PC）上，不是跑在开发板上。**
MCU（Pico 2 / ESP32）是**被驱动的设备**，靠 USB 串口被主机代理。
这本质是 **Firmata（20 年前 Arduino 的答案）的升级版**：变量从裸编号升级为语义化命名，
附加类型/单位/范围/安全边界，接入对象从主机程序变成 AI Agent。
→ **对嵌入式团队的意义：现在就能动手**，用 Firmata 或自定义串口协议把 MCU 变成
"可读写的变量集合"，等规范公开只需换主机侧一层壳，**底层固件不用改**。

## 调研：测试测量仪器与 MHS（示波器 / 万用表 / 逻辑分析仪）

`outputs/测试测量仪器与MHS-示波器万用表逻辑分析仪.md`。

### 核心结论
**官方 MHS 名单里没有一家电子测试测量厂商**（无 Keysight/Tek/R&S/Rigol/Siglent/Saleae）。
一处易混淆点：名单里的 **Danaher 与示波器无关**（Tektronix 已随 Fortive 于 2016 年分拆，
Danaher 现在是生命科学+诊断）。另有一条**待确认**线索：疑似官方架构图的设备标签里出现了
`Oscilloscope`（与 Camera/Microscope/Mass Spec/Laser 并列），但来源无 URL 无法核实。

### 最实用发现：示波器的 MCP server 已经有了（社区做的，不等 MHS）
- **rigol-mcp**（erebusnz，MIT，Python 3.11+，uv，2026-06/07 活跃）：DS1000Z/MSO1000Z + DHO 系列，
  **LAN TCP 5555** + USB；30+ 测量、波形下载(~1200点屏幕缓冲)、截图、**send_raw SCPI 逃生舱**、
  错误队列检查。限制：波形非全存储深度；math/数字通道/协议解码需走 send_raw。
- **siglent-sds-mcp**（MagnusJohansson，TypeScript，MIT）：Siglent SDS，**SCPI over TCP 5025，
  无需 VISA/NI-MAX 驱动**，12 个工具，波形返回电压/时间数组。
- **lecroy-mcp**：LeCroy/Teledyne，SCPI over **VXI-11(LXI)** 或 USB，pyvisa-py；
  **不支持 NI-VSA（破坏截图）**；含 FFT/INTG/DIFF；支持 WaveSurfer/HDO/WaveRunner/WavePro/MDA/SDA。

### 为什么这块最容易接：SCPI 35 年前就"MHS 化"了
**SCPI（1990，基于 IEEE 488.2）：带 `?` = 查询 = read，不带 `?` = 设置 = write，1:1 映射。**
树状命名空间 + 三字母缩写 + 大小写不敏感。
- 公共命令：`*IDN?` `*RST` `*CLS` `*OPC?`（= procedure 轮询）`:SYST:ERR?`（错误队列，要读到 0）
- 万用表：`MEAS:VOLT:DC?` / `MEAS:FRES?`（4线）/ `CONF:VOLT:DC 10,0.0001` / `VOLT:DC:NPLC 10`
- 示波器：`CHAN1:SCAL` `TIM:SCAL` `TRIG:EDGE:LEV` `MEAS:FREQ?` `WAV:DATA?`（Tek 系是 `CURV?`）
- PyVISA：`@py` = **PyVISA-py 纯 Python 后端（免厂商驱动）**；二进制传输比 ASCII 快 5-10 倍；
  **默认超时仅 2 秒**，长采集必超时。错误码 -100/-113/-221/-222/-224。

### 三类设备可行性
- **示波器** ✅ 最成熟（现成 MCP server 或 SCPI over TCP 自己包，几十行 Python）
- **万用表** ⚠️ **分两档**：台表（Keysight 34401A/34461A、Keithley 2000、Rigol DM3058、
  Siglent SDM3045X）SCPI 完整可接；**手持表（Fluke 87 等）无编程接口基本没戏**；
  少数例外如 UNI-T UT61E 有 USB 串口，sigrok 有 `uni-t-ut61e` 驱动。
- **逻辑分析仪** ⚠️ 三条路：
  A **Saleae**（Logic 2 Automation API，**gRPC**，官方开源 .proto + Python 封装，**支持 headless**；
  另有 Logic MSO API；23 内置 + 50+ 社区协议分析器）——
  **重要信号：Saleae 官方文档首页写着 "AI/LLM users: see llms.txt"，厂商在主动适配 LLM**；
  B **sigrok**（libsigrok + libsigrokdecode + **sigrok-cli 命令行可被 Agent 直调** + PulseView +
  fx2lafw；驱动含 saleae-logic-pro/fx2lafw/ols/uni-t-ut61e；**单线程，高采样率必须二进制+缓冲**）；
  C 国产 DSLogic/Kingst 看是否被 sigrok 覆盖。

### 关键判断（本篇最有价值的分析）
**MHS 在测试测量的边际价值 << 在实验室自动化的价值。** 因为实验室原本是散沙（N×M → N+M），
而 T&M 的 SCPI 已统一核心 35 年。MHS 只能补三点：SCPI 缩写语法对 LLM 不友好、
缺单位/安全边界元数据、厂商方言差异（Rigol `:WAV:DATA?` vs Tek `CURV?`）。
**但这三点 MCP server 作者已手工解决**（rigol-mcp 按 family 分支处理 :WAV:DATA?，
lecroy-mcp 内置型号 profile + 保守回退）。
→ **推论：为什么这些项目都做成 MCP 而非 MHS driver？因为 MCP 有公开规范和生态，
MHS 规范未公开还得申请等待名单，作者们等不了。等 MHS 开源时这些位置可能已被占。**
这是 MHS "先闭源打磨再开源"策略的实证风险。

## 诊断：review-markdown-preview 会话前端变卡的原因

用户反映标题为“代码审查与优化建议”的会话（实际对应任务 `review-markdown-preview`，即 markdown-preview 重构 / Streamdown 迁移）越来越卡、前端会卡住。已结合截图与 `larify-desktop` 前端代码做了根因分析。

### 主要结论
不是单一瓶颈，而是**消息列表在每次流式更新时都做全量重建**，本轮会话里工具调用极多、单次 assistant 消息包含大量 part，导致每轮更新都触发 O(总 part 数) 的 JS 工作和重复布局。

### 代码层面的具体原因
- `apps/larify/src/renderer/src/app/interaction/assistant/message-list.tsx:635-638`：`recentItems` 的 `useMemo` 在 `messages` 或 `live` 变化时调用 `recentListItems()`，为**每一条消息**重新生成 `MessageListItem`。
- `message-render-items.ts:156-333`：`buildAssistantRenderItems()` 会遍历消息的每个 part，且每个 text/reasoning part 都走 `textSummary()`。
- `message-render-items.ts:85-99`：`textSummary()` 每次都对前 320 字符执行 `fromMarkdown(prefix)` + `markdownPlainText()` 整棵 mdast 遍历，**没有按 part 缓存**。
- `change-summary.ts:35-56`：`summarizeMessageChanges()` 在 `itemsForMessage()` 里为每条 assistant 消息调用一次，随后 `MessageView` 里如果 `lastFragment` 又调用一次，同一份数据算了两次。
- `message-list.tsx:597`：`updateViewportIndex()` 用 `querySelectorAll('[data-message-index]')` 遍历当前渲染的所有消息元素，滚动/每帧都跑。
- `message-list.tsx:706-723` + `:736-750`：流式过程中 `useLayoutEffect` 反复 `scrollViewportToBottom()` + `autoscrollToBottom()`，且每条消息挂载 `ResizeObserver`，工具结果尺寸变化时触发重排。

### 为什么这个会话特别卡
截图显示该轮处理耗时 4 分 15 秒，包含大量连续的文件读取、任务记录更新、CDP 探针、测试运行。每个工具结果都会更新最后一条 assistant 消息的 parts，从而触发上述整条重建链路。工具调用越多、消息越长，单次更新的 CPU 时间就线性增长，最终主线程被占满，UI 表现为“卡住”。

### 已有优化与仍可改进的点
- 已有：用 `react-virtuoso` 做虚拟滚动、`Message` 用 `React.memo`、`activity-history` 把同类工具调用折叠成群组、近期有 `feat: optimize long conversation navigation`（commit 43e9cd18）。
- 可改进：按 `message.id + partIndex` 缓存 `textSummary`；避免 `summarizeMessageChanges` 重复计算；把 `recentItems` 改成增量更新而非全量重建；对 `updateViewportIndex` 做节流/防抖；长工具输出可考虑延迟展开或截断预览。

## 复测：改动后的剩余性能问题（第二轮，实测数据）

`itemsForMessageCache` 让**历史消息**的重算 O(N)→0，正确。但**正在流式的那条消息**引用每次都变

|---|---|---|
| 100 tool + 100 text | 18.3ms | 183ms/s |
| 300 tool + 300 text | 44.2ms | 442ms/s |
| 600 tool + 600 text | 85.3ms | **853ms/s** |

纯 tool 遍历极便宜（500 tool = 0.126ms），**开销 99~100% 来自 `textSummary`**。

### ★ 根因①：text part 缺 `state` 时缓存永不写入（相差 32~48 倍）
`message-render-items.ts:220`
`partStreaming = part.state === 'streaming' || (part.state === undefined && streaming)`
→ 无 state 的 text part 在 streaming 时 `partStreaming=true` → 传入 `complete=false`
→ `:96` `settled = complete || text.length > 320 || summary.length < normalized.length` 全 false
→ **不写缓存** → 每次 `fromMarkdown()` 重 parse。
- 100 text：无 state **18.06ms** vs state='done' **0.57ms**（32×）
- 300 text：无 state **40.75ms** vs state='done' **0.84ms**（48×）

### ★★ 根因②：`summaryCacheLimit = 500` 缓存颠簸（断崖式，最致命）
缓存是全局 Map 上限 500 条（`:61`，`rememberSummary` 淘汰 `keys().next()` 即最老插入）。
一条消息的 text part 数 > 500 时槽位不够 → 每插一个淘汰一个 → 下一轮遍历全部 miss → 无限颠簸。
- 200 slots: 0.33ms ｜ 400 slots: 1.11ms ｜ **600 slots: 163.50ms** ｜ 900 slots: 250.98ms
- 400→600 暴涨 **148 倍**，@10Hz 占主线程 1635ms/s → UI 完全卡死

**这解释了"越来越卡"：不是线性劣化，是单条消息 text part 累积跨过 500 后的阈值型崩溃。**

## 修复：textSummary 缓存（已实测验证）

改动文件：`apps/larify/src/renderer/src/app/interaction/assistant/message-render-items.ts`

### 方案（关键决策：用 part 而非 message 做 key）
```ts
const summaryCache = new WeakMap<object, SummaryCacheEntry>()   // 原：Map<string, entry> + 上限 500

function textSummary(part: object, text: string): string {
  const cached = summaryCache.get(part)
  if (cached && text.startsWith(cached.prefix)) return cached.summary
  const prefix = text.slice(0, 320)
  const normalized = markdownPlainText(fromMarkdown(prefix)).replace(/\s+/g, ' ').trim()
  const first = sentenceSegmenter.segment(normalized)[Symbol.iterator]().next()
  const summary = first.done ? normalized : first.value.segment.trim()
  summaryCache.set(part, { prefix, summary })   // 无条件写入，去掉 settled 判定
  return summary
}
```

**为什么用 part 而不是 message 做 key**（中途改过一次方案）：
`useChat` 每次流式 tick 都生成新 message 对象（引用必变），用 message 做 WeakMap key 必然 miss。
但 AI SDK 对 part 是**原地 mutation** —— 见
`node_modules/.pnpm/ai@7.0.77_.../ai/src/ui/process-ui-message-stream.ts:451` `textPart.text += chunk.delta`。
该文件对 parts 只有 `push` / 原地 `+=` / `reset-step` 时的 `splice`，**无任何替换已有 part 引用的操作**
（grep `parts[i] =`、`parts.map(` 均无匹配）→ part 引用在流式期间完全稳定。

去掉 `settled` 判定（`complete || text.length > 320 || summary.length < normalized.length`）：
它导致无 `state` 的 text part 在 streaming 时永不写缓存。无条件写入是安全的——命中靠
`startsWith(prefix)`，流式追加天然命中，内容被整体替换时自动 miss 重算。

### 实测效果（单次 buildAssistantRenderItems）
| 场景 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| 无 state text ×100 | 18.06ms | 0.220ms | 82× |
| 无 state text ×300 | 40.75ms | 0.401ms | 102× |
| 跨 500 上限 ×600 | **163.50ms** | 0.735ms | **222×** |
| 跨 500 上限 ×900 | 250.98ms | 0.835ms | 301× |
| 真实流式 settled=1200 | 85.3ms | 0.489ms | 174× |

**600/900 个 part 的断崖消失** —— 与 200 个 part 同样在亚毫秒级，不再有阈值型崩溃。
@10Hz 从占用主线程 853~2510ms/s 降到 5~8ms/s。

  固件项目的 AGENTS.md 必须比 Web 项目更指令式（堆上限、ISR 时长预算、禁用动态分配等）。
- **厂商开始把 MCP 当基础设施**：乐鑫内置进 ESP-IDF v6.0；Saleae 官方 llms.txt。
  对比 MHS 规范未公开、SDK 拿不到、要申请排队——**厂商已用脚投票**。
- **选型实用判据**：设备已有标准化程序化描述（SVD/SCPI/开放 API）→ 直接用 MCP，别等 MHS；
  只有"每台设备都要手写集成"的场景才值得等 MHS。

### 核心事实
- DeepSeek 官方视觉模型 `deepseek-v4-flash-vision-exp` 于 **2026-08-21** 上线（实验性）。
  同目录下 `deepseek-v4-flash` / `deepseek-v4-pro` **纯文本，发图返回 400**。
- DeepSeek API **原生支持 Responses API**（`base_url = https://api.deepseek.com/`），
  这正是 Codex 用的协议 → **不需要 LiteLLM/CC-Switch 之类代理，也不需要降级 wire_api="chat"**。
- 官方 Codex 接入文档菜单：1=flash, 2=pro, **3=deepseek-v4-flash-vision-exp**, 9=恢复默认。

### 配置要点（Windows: %USERPROFILE%\.codex\）
- 一键脚本（PowerShell）：`irm https://cdn.deepseek.com/api-docs/codex-deepseek-setup-en.ps1 | iex`
- 两个文件缺一不可：
  - `config.toml`：`model` / `model_provider="deepseek"` / `preferred_auth_method="apikey"` /
    `forced_login_method="api"` / `model_reasoning_effort="high"` / `model_catalog_json`，
    以及 `[model_providers.deepseek]`（base_url 末尾带斜杠、wire_api="responses"、密钥）。
  - `models.json`：模型元数据。**关键是 `input_modalities: ["text","image"]`** —— 这是告诉
    Codex「这个模型能吃图」的唯一开关；视觉条目还带 `supports_image_detail_original: true`。
    文件很大（含完整 base_instructions 提示词），官方脚本生成，不要手敲。
- 官方脚本把密钥明文写进 `experimental_bearer_token`；更安全的做法是改 `env_key = "DEEPSEEK_API_KEY"`。
- 硬门槛：Codex CLI ≥ **0.144.0**（models.json 里的 `minimal_client_version`）。

### 坑
- 图片只允许出现在 user/developer 消息，system/assistant 位置会 400。
- 图片按尺寸缩放到约 800×800，**单图 token 封顶 384**，多图独立计算。
- 不支持 `previous_response_id` / `store`（无状态 API），Codex 自己处理。
- Exp = 实验性，模型 ID 可能变；建议用 profile 隔离，别覆盖默认配置。
- 切换 provider 后旧会话"消失"是假的——Codex 按登录方式分组会话历史。
- 峰谷计费：UTC 01:00-04:00 与 06:00-10:00（北京 9-12 点、14-18 点）工作日 2 倍价。
- 改完配置需**完全重启** CLI / 桌面端 / VS Code 插件。

### 社区实况调研（第二轮，用 gh 查 openai/codex issue 区）

**官方 setup 脚本生成的 models.json 有三个字段会踩坑，三个模型条目（含 vision-exp）全中：**
`supports_search_tool=true` + `tool_mode=null` + `multi_agent_version="v2"`。

已验证的社区补丁（改 models.json 两个字段，无需改 Codex 源码）：
- `supports_search_tool: true` → **false** —— 解决 MCP 工具静默不可见。
  根因：`spec_plan.rs` 里 `search_tool_enabled = supports_search_tool && namespace_tools`，
  为真时 `mcp_tool_exposure.rs` 把所有 MCP 工具注册成 `ToolExposure::Deferred`，
  而 `tool_mode:null` 又解析成 `ToolMode::Direct`，没有 code-mode exec 可嵌套 → 工具全隐藏。
  独立验证：TunaTung(Win11/0.146)、kyambuthia(Linux/0.147)、TOV1C。
- `multi_agent_version: "v2"` → **"v1"** —— 解决子 agent 收不到任务。
  根因：MultiAgentV2 的 task payload 走 `InterAgentCommunication::new_encrypted`，内容塞在
  `encrypted_content` 块里；DeepSeek Responses 兼容表只认 message / function_call /
  function_call_output / reasoning / web_search_call，`agent_message` 整个 item 被丢弃
  → 子 agent 只看到空 `Payload:`，表现为"我没收到任务"。

相关 issue：#36382(MCP)、#36586/#36493/#36321/#37237/#37822(子agent)、
#37825(Code Mode 的 exec 是 custom tool，DeepSeek 只支持 apply_patch → 报错)、
#37379/#29156(桌面端隐藏自定义 provider)、#23186/#36942(MCP namespace 包装)。

其他坑：
- `tool_search` 双重损坏：Codex 发 `type:"tool_search"`（无 function 字段）→ LiteLLM 等中转 400；
  改造成普通 function → 又被 Codex 自己的 handler 拒。中转链路上这个逃生口完全不可用。
- 中转链路（LiteLLM/sglang）丢 `reasoning_content` 会 400。
- 桌面端 Microsoft Store/UWP 版访问不了 localhost 代理。
- 反例：AiKit 里写 `experimental_bearer_token = "{$env:DEEPSEEK_API_KEY}"` 是无效写法，
  Codex 不会展开 PowerShell 变量语法，正确做法是 `env_key = "DEEPSEEK_API_KEY"`。

社区方案分四派：官方脚本派（主流但带 bug）／**补刀派**（脚本+改两字段，最实用）／
打补丁派（CCanxue/codex-deepseek-subagent-fix，改 Codex 源码保持 v2，12★，需自编译）／
代理派（LiteLLM、CC-Switch 130k★、codex-relay——多为 2025 年 DeepSeek 不支持 Responses
时的遗留方案，现在除非要多家中转，否则不必）。

产出文件：outputs/deepseek-codex-models.json（官方原版）、
outputs/deepseek-codex-models.patched.json（应用社区补丁版）。

## 修复 `npm run dev:preview` 报 "'electron-vite' 不是内部或外部命令"

### 根因
根目录 `node_modules` **安装残缺**：完全没有 `.bin/` 目录，`electron-vite` / `vite` 包缺失，
`node_modules/electron` 只剩 `dist/`（连 `package.json` 都没有）。说明之前某次 `npm install`
被中断（Ctrl+C 或杀软占用）。脚本本身没写错，是 CLI 不存在。
排查提醒：`ls node_modules` 看不到 `.bin`（点号开头），要用 `ls -a` 或直接检查 `node_modules/.bin/<cmd>`。

### 修复过程
1. 先删残缺的 `node_modules/electron`，再重装。
   - **Git Bash 的 `rm -rf` 会失败**：环境自带 safe-delete 钩子拿到 `/d/Workspace/...` 这种
     POSIX 路径，报 `relative path rejected (must be absolute)`。
   - 解法：**PowerShell + Windows 绝对路径**
     `Remove-Item -LiteralPath 'D:\...\node_modules\electron' -Recurse -Force -Confirm:$false`。
2. `npm install --no-audit --no-fund` 约 23 分钟（主要是重下 electron 二进制，镜像在 `.npmrc`
   的 npmmirror）。结果 `added 931 packages, changed 370 packages`，postinstall 的 `patch-package`
   打了 3 个补丁（allotment / defuddle / linkedom）。
3. 验证：`node_modules/.bin` 198 个命令，`electron-vite/5.0.0` 正常；`electron-vite build`
   能跑到 "161 modules transformed"。

### 遗留 / 未解决
- vite 构建前 `emptyOutDir` 清空 `apps/larify/out` 时被 sandbox 的 safe-delete 拦截
  （`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，单轮删除计数阈值 50）。**这是沙箱限制不是项目问题**，
  用户在自己终端跑不会有。
- `node_modules/` 残留 48 个 npm 临时 staging 目录（`.rc-util-xxxxx` 等），同为上述保护导致
  npm 清理失败，无害但占空间。
- `apps/larify/out`、`apps/larify/dist` 均为 gitignore 的构建产物（`git ls-files` 为空），可安全删除。

### 用户偏好
- 对删除操作很敏感，会拦截批量删除请求。涉及删除前务必先说清删什么、为什么删。

## 修复：右侧工作台文件树图标与文件名未垂直居中

用户反馈右侧工作台（文件树）里文件图标和文件名看起来没居中。

**根因**：`apps/larify/src/extensions/workspace/renderer/explorer/workspace-tree.tsx` 的 `TreeTitle` 中，文件名 `<span>` 继承外层 `.rc-tree-treenode` 的 `line-height: 26px`，而 `FileIcon` 只有 `16px`。虽然外层用了 `items-center`，但文字行高盒子比图标高，中文字体视觉基线又偏低，导致图标看起来没在文字视觉中间。

**改动**：把 `TreeTitle` 高度锁为 `16px`（`h-4`），并把文件名行高也改成 `16px`（`leading-4`），使图标与文字盒子同高、中心对齐。

**验证**：
- `workspace-tree.test.ts` 33 例全绿
- `npm run typecheck` 通过
